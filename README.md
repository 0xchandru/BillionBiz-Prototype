# BillionBiz – Multi-Tenant Commerce & Business Management Platform

BillionBiz is a production-ready, multi-tenant merchant commerce operating platform. Merchants can register, build, and publish custom online storefronts (supporting Commerce, Services, or Both), manage products, inventory, orders, customer CRM, appointments, POS registers, staff permissions, and analytics from a unified Admin Portal.

---

## Architecture Overview

- **`billionbiz-frontend/`**: Vite + React + TypeScript single-page application powering:
  - Landing & Store Registration (Minimal, streamlined OTP flow)
  - Merchant Admin Portal (Dashboard, Orders, Catalog, Appointments, People/CRM, POS & Counters, Online Store, Team, Settings)
  - Dedicated Cashier POS Terminal
  - Multi-Tenant Storefront Engine & Visual Store Editor
- **`billionbiz-backend/`**: Express + TypeScript + SQLite / PostgreSQL authoritative backend:
  - Multi-tenant tenant isolation and schema migrations
  - Unified Single-Input OTP Authentication (Email / SMS via Resend / Twilio)
  - Google OAuth Integration
  - Realtime WebSocket Gateway & Transactional Outbox
  - End-to-end unit & integration test suite (Vitest)

## Backend Windows Service & `bbiz` CLI

The backend can run permanently as an **Automatic Windows Background Service** on boot, managed globally using the `bbiz` CLI:

```bash
# Check status (port 8080, DB, Cloudflare tunnel)
bbiz status

# Start / Stop / Restart
bbiz start
bbiz stop
bbiz restart

# Live logs & health test
bbiz logs -f
bbiz health

# Install as an automatic service on laptop boot
bbiz service install
```

## Quick Start

### 1. Backend Setup
```bash
cd billionbiz-backend
npm install
npm run dev
```
Backend runs on `http://localhost:8080`.

### 2. Frontend Setup
```bash
cd billionbiz-frontend
npm install
npm run dev
```
Frontend runs on `http://localhost:5173`.

### 3. Storefront Runtime

`billionbiz-frontend/storefront-runtime/` is the shared React storefront application. It uses the same `StorefrontPage` and `StorefrontRenderer` modules as the editor preview, resolves the requested hostname to an active store, and fetches only that store's published release. Merchant projects remain separate build artifacts generated by the backend; they do not each run a permanent Node/Vite server.

```bash
# Start each service in its own terminal
npm run dev:backend
npm run dev:editor
npm run dev:storefront

# Or start all three together (Ctrl+C stops the services)
npm run dev:all
```

The storefront runtime listens on `STOREFRONT_PORT` (default `3000`), and reads `VITE_API_BASE_URL` (default `http://localhost:8080/api/v1`) and `VITE_ROOT_DOMAIN`. Build a production static bundle with `npm run build:storefront`, then serve it with `npm run start:storefront`. The static production server also defaults to port 3000 and binds to `0.0.0.0`, which makes it reachable by the existing Cloudflare Tunnel origin.

Local preview can use `http://localhost:3000/store/<store-slug>` or `http://<store-slug>.localhost:3000`. For realistic public-host testing, route `*.chandraprakash.codes` to the same runtime and use a valid active store slug. The editor may continue running at `localhost:5173`; the public storefront no longer depends on the editor dev server.

#### Cloudflare Tunnel and production

The current tunnel route shown in Cloudflare is already the required shape: keep `api.chandraprakash.codes` → `http://localhost:8080` above `*.chandraprakash.codes` → `http://localhost:3000`. The runtime reserves internal subdomains and will never render them as merchant stores. No per-store DNS records or additional tunnel are needed. No Cloudflare dashboard configuration was changed by this implementation.

`localhost:3000` is a development/tunnel origin only. For production, build and run the shared runtime on managed infrastructure, then update the tunnel's wildcard service to that reachable runtime origin; keep the API route on the backend origin. Do not point production traffic at a developer laptop. Store readiness is reported only after DNS resolves and HTTPS responds on the store hostname.

#### Store Media Uploads

Product, category, and bundle image uploads use short-lived Cloudflare R2 presigned PUT URLs. Configure `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`, and `R2_PUBLIC_BASE_URL` in the backend environment. Set bucket CORS to allow `PUT` from the admin origin with the `Content-Type` request header. Keep the R2 secret in the backend environment only.
